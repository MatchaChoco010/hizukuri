# リリースを切る

リリースは、人が、ここまでの変更を確認するための区切りである。`develop` に入った変更を `release` に取り込み、
何が入ったかを報告するスライドを作り、`main` への PR を用意する。`main` への merge は、人が確認して、承認した後に行う（下の「リリースの後」）。
リリースを切るときには、merge しない。

ブランチの役割は、`AGENTS.md` の「ブランチと、変更の流れ」にある。

## 引数

| 引数 | 内容 |
| --- | --- |
| 出力先のディレクトリ | スライドの pdf を置く場所。**リポジトリの外**のディレクトリ。必須。与えられていなければ、尋ねる |

スライドは、リポジトリに commit しない。

## 手順

### 1. 前提を確かめる

1. `git fetch --tags origin` する。作業ツリーに、未 commit の変更が無いこと。
2. `origin/develop` の先頭で、CI（`ci.yml` と `vm.yml`）が通っていること（`gh run list --branch develop`）。
   通っていなければ、リリースを切らずに、何が落ちているかを報告する。
3. 前回のリリースを見つける。リリースを切るたびに、`release` の先頭に、tag `release-<YYYYMMDD>-<連番>` を打つ（下の 3）。
   いちばん新しい tag が、前回のリリースである。tag が 1 つも無ければ、今回が最初のリリースで、範囲は `main..develop` になる。
4. 前回のリリースから、`develop` に新しい変更が無ければ、切るものが無いことを報告して、終わる。

### 2. 今回の範囲を決める

- 範囲は、「前回のリリースの tag が含む `develop` の commit」から、「いまの `origin/develop`」までである。
- この範囲で `develop` に merge された PR と、閉じられた Issue を、一覧にする
  （`gh pr list --base develop --state merged`、`gh issue list --state closed` と、`git log` の範囲を突き合わせる）。
- PR を通らずに入った commit があれば、それも一覧に入れる（報告から、漏らさない）。

### 3. `release` に取り込む

1. `release` ブランチが無ければ、`origin/main` から作る。
2. `release` に、`origin/develop` を merge する（`git merge --no-ff`。merge commit のメッセージは `Release <YYYYMMDD>-<連番>`）。
   `release` に、直接の変更を commit しない。衝突したら、止めて、報告する（`release` に `develop` 以外の変更が入っていることになる）。
3. tag `release-<YYYYMMDD>-<連番>` を、その merge commit に打つ。日付は UTC。連番は、同じ日の中で 1 から。
   1 日に何度リリースを切っても、連番が進むだけで、前のものを上書きしない。
4. `release` と tag を push する。

### 4. `main` への PR を用意する

- `release` から `main` への、開いている PR が無ければ、作る。あれば、それを使う
  （人が、前回のリリースをまだ merge していないとき、同じ PR に、今回の分が積み上がる）。
- PR の description に、今回のリリースの節を足す（前のリリースの節は、消さない）。節には、次を書く。
  - リリースの名前（tag）と、取り込んだ `develop` の commit
  - 今回の範囲に入った PR と Issue の一覧（番号と題名）
  - 確かめ方の要点（スライドの最後のページと同じ内容を、短く）
- PR の番号を控える。スライドに書く。

### 5. スライドを作る

skill `release-slides` を使う。渡すものは、次のとおり。

| 渡すもの | 内容 |
| --- | --- |
| 範囲 | 前回のリリースの tag と、今回の tag。最初のリリースでは、`main` と、今回の tag |
| リリースの名前 | 今回の tag |
| PR | `main` への PR の番号と URL |
| 出力先 | この skill が受け取った、出力先のディレクトリ |

- **スライドは、リリース 1 回につき 1 つ作る。** 前のリリースのスライドを、上書きしない。
  人の確認で直しが入り、もう一度リリースを切ったときは、前回のリリースからの差分のスライドを、新しく作る。
- スライドの中身と作り方は、`release-slides` が決める。この skill は、何を渡すかだけを決める。

### 6. スライドを、PR に付ける

- PR に pdf を添付できる手段があれば、添付する。
- 添付できなければ（`gh` には、PR に file を添付する機能が無い）、スライドは、出力先に置くだけにする。
  PR の description から、スライドへのリンクを張らない（リポジトリの外の場所を、PR に書かない）。
  どの PR のスライドかは、スライドに書いた PR の番号で分かる。

### 7. 報告する

次を、頼んだ人に伝える。

- リリースの名前（tag）、`main` への PR の URL
- スライドの pdf の場所
- 今回の範囲に入った PR と Issue の数
- 確かめ方（スライドの最後のページにあるものを、そのまま）

## リリースの後

- 人は、スライドを読み、`release` を動かして確かめる。問題が無ければ、merge を承認する。
- **承認を受けたら、`main` への PR を merge する**（merge commit で。`gh pr merge --merge`）。承認するのは人で、merge の操作は、エージェントが行う。
  承認されたのが、どのリリース（tag）までかを確かめる。PR の先頭が、承認されたリリースより進んでいたら、merge せずに、その旨を伝える。
  承認の無いまま、merge しない。
- 問題が見つかったら、直しを `develop` に入れる（`feature/<名前>` のブランチと PR で）。`release` を、直接直さない。
  直しが `develop` に入ったら、この skill を、もう一度使う。前回のリリースからの差分で、新しいリリースと、新しいスライドができる。
- 人が確認しないまま、次のリリースの時機が来たら、そのまま次のリリースを切る。`main` への PR には、確認されていない分が積み上がる。
