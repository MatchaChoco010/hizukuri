# リリースの報告のスライドを作る

リリース 1 回につき、スライド（pdf）を 1 つ作る。読む人は、このスライドだけを見て、何が入ったかを把握し、
`release` を動かして確かめ、`main` に入れてよいかを決める。

リリースを切る流れ（`release` への取り込み、tag、`main` への PR）は、skill `release` にある。この skill は、スライドだけを作る。

## 引数

| 引数 | 内容 |
| --- | --- |
| 範囲 | 前回のリリースの tag と、今回の tag。最初のリリースでは、`main` と、今回の tag |
| リリースの名前 | 今回の tag（`release-<YYYYMMDD>-<連番>`） |
| `main` への PR | 番号と URL。スライドの表紙と、各ページの下に出る |
| 出力先 | スライドを置くディレクトリ。**リポジトリの外**。必須。与えられていなければ、尋ねる |

単独で使うとき（スライドの出来を調整するとき、作り直すとき）は、範囲を、任意の 2 つの revision で指定する。
名前は、既にあるスライドと重ならないものにする。`main` への PR が無ければ、`pr: none` とする。

## 出力

```text
<出力先>/<名前>/
  hizukuri-<名前>.pdf     スライド
  slides.typ              スライドのソース
  lib/                    テンプレートの写し
  img/                    取り込んだ画面
  scenes/                 画面を取り込んだスクリプト
  inventory/              範囲に入った PR、Issue、commit の一覧
  preview/                各ページの PNG（`build.sh --preview`。見て確かめるためのもの）
```

- **前のリリースのスライドを、上書きしない。** `scripts/new-deck.sh` は、同じ名前のディレクトリがあれば、何もせずに失敗する。
- スライドも、画像も、リポジトリに commit しない。
- pdf を作った材料を、同じディレクトリに残す。後で、同じ pdf を作り直せる。

## 道具

| もの | 内容 |
| --- | --- |
| `scripts/new-deck.sh OUT_DIR NAME` | スライドのディレクトリを作り、`slides.typ` の骨組みを置く |
| `scripts/collect.sh BASE HEAD OUT_DIR` | 範囲に入った PR、Issue、PR を通らずに入った commit を、一覧にする。`gh` で読む。何も変えない |
| `capture/run-scene.sh OUT_DIR SCENE.sh...` | 検証用の compositor を、画面なしで動かして、画面を取り込む |
| `capture/headless.sh` | 画面を取り込むスクリプト（scene）が使う関数 |
| `scripts/build.sh DECK_DIR [--preview]` | pdf を作る。`--preview` で、各ページの PNG も書く |
| `template/hizukuri-slides.typ` | テンプレート。部品の一覧は、下の「テンプレートの部品」 |

- pdf は、[Typst](https://typst.app/) で組む。Typst と、フォント（Noto Sans CJK JP、JetBrains Mono）は、`flake.nix` の `slides` の devShell が、
  `flake.lock` の nixpkgs から用意する。機械に入っている Typst とフォントは、使わない（`--ignore-system-fonts`）。
  どの機械でも、同じソースから、同じ pdf ができる。
- Typst の package（インターネットから取得するもの）は、使わない。図も、テンプレートの部品で組む。
- 要るのは、Nix と、`gh`（ログインしていること）である。画面の取り込みで VM を使うときは、KVM も要る（`docs/dev/vm-environment.md`）。

## 手順

### 1. ディレクトリを作る

```sh
.claude/skills/release-slides/scripts/new-deck.sh <出力先> <名前>
```

### 2. 範囲に入ったものを集めて、読む

```sh
.claude/skills/release-slides/scripts/collect.sh <前回の tag> <今回の tag> <出力先>/<名前>/inventory
```

`inventory.md` に、merge された順の PR、PR が閉じる Issue、**PR を通らずに入った commit** が並ぶ。PR と Issue ごとに、
description と議論を書いたファイル（`pr-<番号>.md`、`issue-<番号>.md`）ができる。

読むものは、次のとおりである。**commit のメッセージと、PR の題名だけから、書かない。**

- PR と Issue の description と議論。何を、なぜ変えたか。
- 差分（`git diff <前回>..<今回> -- <場所>`、`git show <commit>`）。description に書かれていない変更が、入っていないか。
- 変更が触れた部分の、いまの文書（`docs/`）とコード。その変更の前に、どうなっていたか（`git show <前回>:<ファイル>`）。
- 分からないことは、動かして確かめる。推測で埋めない。

### 3. 項目を決める

- **項目の単位は、PR である。** Issue と、それを閉じる PR は、1 つの項目にする。1 つの Issue に PR が複数あれば、まとめて 1 つの項目にする。
- PR を通らずに入った commit は、まとまった作業の単位ごとに、項目にする。どの項目にも入らない commit を、残さない。
- 順番は、`develop` に入った順である。
- 範囲のすべての commit が、どれかの項目に入っていることを、最後に確かめる。
- 項目ごとに、種類（下の表）、部分（変わったのは、プロジェクトのどこか）、題（何が、どうなったか）を決める。

| 種類 | 使うとき |
| --- | --- |
| `追加` | 無かったものが、できるようになった |
| `修正` | 意図と違う動きを、直した |
| `変更` | 動いていたものの、動きや作りを変えた |
| `削除` | あったものを、無くした |
| `文書` | 文書だけが変わった |

### 4. 画面を取り込む

下の「画面の取り込み方」のとおりに、項目ごとに、要る場面を決めて、取り込む。

### 5. 書く

`slides.typ` を書く。下の「どう書くか」と「テンプレートの部品」に従う。

### 6. 組んで、見て確かめる

```sh
.claude/skills/release-slides/scripts/build.sh <出力先>/<名前> --preview
```

- ページに収まらないスライドと、折り返してしまうコードの行があると、一覧を出して、失敗する。分けるか、短くする。文字を小さくして収めない。
- **`preview/` の PNG を、全ページ、見て確かめる。** 見るのは、文字の重なり、画像の中身が読めるか、表の列の幅、空きすぎたページ、
  識別子の前後の余計な空白である。
- 項目の一覧のページの、リンクとページ番号が合っていること。

### 7. 確かめ方のページを書く

下の「確かめ方のページ」に従う。**書いたコマンドは、そのとおりに実行して、書いたとおりになることを確かめる。**

### 8. 報告する

pdf の場所、項目の数、ページ数を伝える。迷った点（項目の分け方、省いたもの、取り込めなかった画面）があれば、伝える。

## どう書くか

### 読む人

- hizukuri が何を目指しているかは、知っている。
- その変更の背景、議論、コードは、知らない。前回のリリースより前のことも、覚えていない前提で書く。
- スライドだけを読む。PR も、コードも、開かずに、「どういう仕組みが入ったか」を把握したい。
- 読んだ後に、自分で動かして確かめ、`main` に入れてよいかを決める。

### 全体の構成

| 部分 | ページ | 内容 |
| --- | --- | --- |
| 表紙 | 1 | リリースの名前、日付、範囲、取り込んだ `develop` の commit、`main` への PR、項目の数 |
| 今回のリリースの要点 | 1 | このリリースで何が変わったかを、利用者から見た言葉で、3〜5 個。まだ無いもの、気を付けることも、ここに書く |
| 全体の構成と、項目の対応 | 0〜1 | 項目が多いとき（目安は 8 個以上）と、複数の項目が 1 つの仕組みを作っているとき。図に、項目の番号を付ける |
| 項目の一覧 | 1 | `#item-list()` が作る。番号、種類、部分、内容、Issue と PR へのリンク、ページ |
| 項目 | 項目ごとに 1〜6 | 下の「1 つの項目の組み立て」 |
| 確かめ方 | 2〜5 | 下の「確かめ方のページ」 |
| 付録 | 0〜1 | PR を通らずに入った commit の一覧（あるときだけ） |

### 1 つの項目の組み立て

項目の上の帯に、番号、種類、部分、題と、**Issue と PR へのリンク**が出る（`#item` の `refs`）。リンクは、必ず付ける。

最初のページは、**題**（そのページで言いたいことを、1 文で）と、**lead**（何が入ったか、何のためか。2〜3 文）で始める。
lead だけを拾い読みしても、リリースの全体が分かるように書く。

その後は、種類ごとに、次の順で書く。

| 種類 | 書く順 |
| --- | --- |
| 追加 | 何ができるようになったか → 仕組み（登場するもの、流れ、どこからどこまでを受け持つか）→ 使い方と、見え方（画面、コマンド）→ いまの制約と、未実装のもの |
| 修正 | 何が起きていたか（症状、どういうときに起きるか、だれが困るか）→ 原因 → どう直したか → 影響する範囲 → どう確かめたか |
| 変更 | 以前は、どうだったか → どう変えたか → なぜ → 使う側が、変えることになるもの |
| 削除 | 何を無くしたか → なぜ → 代わりになるもの |
| 文書 | 何を書いたか → 何が決まり、何が決まっていないか |

ページ数の目安は、小さな修正と変更が 1 ページ、機能の追加が 2〜4 ページ、仕組みが大きく入ったときが 4〜6 ページである。
1 ページには、1 つの主題だけを書く。収まらなければ、主題を分けて、ページを足す。

### 文

- 日本語で、「である」の文体で書く。技術用語と識別子は、原語のまま書く。
- **最初に出てくる言葉は、説明する。** その変更で初めて出てくる名前、略語、内部での呼び名は、括弧で一言を添える
  （「Smithay（Rust の、compositor 用のライブラリ）」）。
- 「何が」「何を」を省かない。主語の無い文を、続けない。
- **変更の前後が分かるように書く。** 追加なのか、修正なのか、前はどうだったのかが、文から読み取れること。
- 事実だけを書く。数、版、既定の値、コマンドは、コード、文書、実行した結果で確かめたものを書く。
- **未実装のものと、制約を、隠さない。** `#note` で、目に付く形にする。
- 理由を書く。「こうした」だけでなく、「こうしないと、何が起きるか」を書く。

### 粒度

- 書くのは、**仕組み**である。登場するもの、その間の流れ、境界（だれが、何を受け持つか）、利用者から見える動き。
- ファイルの名前、crate の名前、関数の名前は、「どこの話か」を示すのに要る範囲で書く。
- **書かないもの**: どのファイルの、どの行に、何を足したか。変更したファイルの一覧。diff の要約。内部の変数や、補助の関数の名前。
- 表は、読む人が見比べるもの（選択肢、起動時の指定、経路、前後の違い）に使う。文書の表を、そのまま写さない。要るものに絞る。

### 画面と図

- **見た目に出る変更には、画面を付ける。** ウィンドウの見え方、配置、色、画面に出るもの、端末に出る結果。
- 画面には、caption を付ける。何が写っているか、どう取り込んだか（headless か VM か、どの指定で起動したか）、どこを見るかを書く。
- 仕組みは、図にする（`#flow`、`#layers`）。層、流れ、境界は、文より、図のほうが伝わる。
- 端末に出る結果（検査の結果、状態の一部）は、実際の出力から、要る行を、そのまま抜いて載せる。書き換えない。
- 取り込めなかった画面を、作らない。似た別の場面で、代わりにしない。

### 避ける書き方

- **commit のメッセージや、PR の題名を、並べる。** 中身を読み、解釈して、文章にする。
- 「〜を改善した」「〜に対応した」「〜を整理した」で終わる文。何が、どう変わったかを書く。
- 作業の経緯（試したこと、やり直したこと、だれが何を言ったか）。書くのは、入ったものである。
- 確かめていない数字、「高速に」「安全に」のような、裏付けの無い評価。
- 特定の機械に固有の情報（ユーザー名、ホスト名、ホームディレクトリのパス、機器の型番）。画面にも、写り込ませない。
- 1 ページに詰め込むこと。文字を小さくして収めること。

### Typst のソースの書き方

- **段落と、箇条書きの 1 項目は、ソースの 1 行に書く。** 行の途中で折り返すと、折り返した場所に、空白が入ることがある。
- **識別子、コマンド、パス、キーの名前は、必ず `` ` `` で囲む。** 囲まないと、`_`、`*`、`#`、`@`、`<`、`$`、`~` が、Typst の記法として解釈される。
- 強調は、`*...*` を使う。`*` の後ろに、空白を入れない（`*強調。*続き`）。
- コードブロックの 1 行は、枠の幅に収める。長いコマンドは、`\` で分けるか、shell の関数にまとめる。

## 確かめ方のページ

スライドの最後に、**ここまでの成果物を、読む人が、自分で確かめる方法**を書く。

- 最初のページは、準備と、全部の検査である。確かめる対象の取り出し方（リリースの tag）、検査のコマンド、要るもの。
- その後に、**今回のリリースで入ったものを、動かして見る手順**を書く。項目ごとの「使い方」のページのコマンドを、
  ここに、順に実行できる形でまとめる。
- コマンドごとに、**何が起きれば正しいか**を書く（`#step`）。何を見るか、どの値が出るか、どのキーで何が起きるか。
- 画面を取る操作（DRM/KMS の session）は、検証用の VM の中で行う手順を書く。読む人の機械の画面を取る手順を、書かない。
- 時間のかかるもの、大きな取得が要るものは、その旨を書く。
- **書いたコマンドは、すべて、そのとおりに実行して確かめる。** 確かめられなかったもの（ウィンドウを出す操作など）は、
  同じことを、画面なしで確かめたうえで載せる。
- 自動の検査を、スライドを作るときに回した結果（通った数）を書く。回していない検査の結果を、書かない。

## 画面の取り込み方

**どの変更に、どの場面の画面を付けるかは、変更の内容を読んで決める。** 目安は、次のとおりである。

| 変更 | 場面 | 手段 |
| --- | --- | --- |
| ウィンドウの見え方、配置、描画、色 | その動きが出ている場面。前後を比べられるなら、2 枚 | headless |
| クライアントとのやり取り（popup、selection、入力） | 実際のアプリで、その操作をした直後 | headless |
| スクリプトの層 | スクリプトが描いた画面、故障したときの画面 | headless |
| DRM/KMS の session、VT の切り替え、複数の出力、hotplug | VM の中の session の画面 | VM |
| 検査、道具 | 端末に出る結果 | 出力を、コードブロックに載せる |
| 文書、CI、内部の作りだけの変更 | 画面は、要らない。図か、表で説明する | |

### headless

検証用の compositor は、画面なしで動かして、制御口から、画面を取り込める（`docs/prototype/README.md`）。
場面ごとに、scene（bash のスクリプト）を書いて、`<出力先>/<名前>/scenes/` に置く。

```sh
.claude/skills/release-slides/capture/run-scene.sh <出力先>/<名前>/img <出力先>/<名前>/scenes/tiles.sh
```

```sh
# scenes/tiles.sh
source "$HZ_LIB"
hz_start --renderer script --wm script --output-size 1920x1080 --output-scale 2 --background 30405c
shell="$(hz_script shell <<'SH'
#!/bin/sh
printf 'foot\r\n\r\n$ '
exec cat
SH
)"
hz_app foot --font="JetBrains Mono:size=11" "$shell"
hz_wait_windows 1
hz_settle 1
hz_shot tiles                      # img/tiles.png
hz_ctl state > "$HZ_OUT/tiles.state.json"
hz_ctl quit >/dev/null
```

| 関数 | 内容 |
| --- | --- |
| `hz_start [指定...]` | compositor を、headless で起動する。描画は、lavapipe |
| `hz_client [指定...]` | 検証用のクライアント（`hizukuri-test-client`）を出す |
| `hz_app CMD...` | 実際のアプリを、その中で起動する |
| `hz_script NAME` | 標準入力を、実行できるファイルにして、パスを返す（端末の中の shell の代わりに使う） |
| `hz_wait_windows N`、`hz_settle [秒]` | ウィンドウが N 個になるまで待つ。描く予定のフレームが無くなるまで待つ |
| `hz_ctl ...` | `hizukuri-ctl`。入力の注入、ウィンドウの移動、スクリプトの呼び出しなど |
| `hz_window_id PATTERN` | 題名か app id に PATTERN を含むウィンドウの id |
| `hz_shot NAME` | 画面を、`img/NAME.png` に書く |

- **出力は、`--output-size 1920x1080 --output-scale 2` にする。** 論理的には 960x540 で、スライドの上で文字が読める大きさになり、
  拡大しても、粗くならない。
- **端末の中で、本物の shell を動かさない。** プロンプトに、ユーザー名と機械の名前が出る。`hz_script` で、決まった文字を出すスクリプトを作って、渡す。
- アプリの文字は、スライドと同じフォントで描かれる（`run-scene.sh` が、fontconfig を、`slides` の devShell のフォントだけに向ける）。
- 画面と一緒に、制御口の `state` を保存しておくと、caption と本文に書く値（位置、変換の列、モード）を、そこから取れる。
- compositor もアプリも、専用の `XDG_RUNTIME_DIR` の中だけで動く。動いているデスクトップには、つながらない。ウィンドウも出ない。
  起動したプロセスは、起動したときの id で止める。終わると、作業用のディレクトリを消す。

### VM

DRM/KMS の session の画面は、検証用の VM の中で動かして、VNC から取り込む（`docs/dev/vm-environment.md`）。

```sh
tools/vm/vm status                                   # 止まっていることを確かめる
nix develop --command tools/vm/try-hizukuri          # ビルド、起動（画面なし）、送付
tools/vm/vm tty-run -- hzk script --seconds 120      # VT の上で、session として起動する
tools/vm/vm move 700 300 && tools/vm/vm click        # 入力を送る
tools/vm/vm screendump <出力先>/<名前>/img/vm-script.png
tools/vm/vm key ctrl-alt-backspace                   # compositor を終わらせる
tools/vm/vm stop
```

- **始める前に、VM が止まっていることを確かめる。** 自分が起動していない VM が動いていたら、触らない。終わったら、止める。
- VM を、ウィンドウに出さない（`--gtk` を付けない）。
- ゲストの利用者と機械の名前（`hizukuri@hizukuri-vm`）は、どの機械でも同じなので、写ってよい。

## テンプレートの部品

`slides.typ` は、`lib/hizukuri-slides.typ` を import して書く。骨組みは、`template/skeleton.typ` にある。

| 部品 | 内容 |
| --- | --- |
| `#show: deck.with(release:, date:, range:, commit:, pr:, repo:)` | 全体の設定。`pr` は `(number:, url:)` か `none` |
| `#title-slide()` | 表紙 |
| `#summary-section()`、`#verify-section()`、`#appendix-section()` | 項目ではないページの区切り（「この報告の内容」「確かめ方」「付録」） |
