# デザインの方針

hizukuri が何であり、何を作るかを書く。ここに書くのは、決まっていることだけである。

## 1. hizukuri は何か

- hizukuri は、**Wayland compositor を作るための基盤**である。
  ゲームエンジンが、ゲームを作るための基盤であるのと、同じ関係にある。
  リアルタイムグラフィクスとスクリプティングで、Wayland compositor の動作を作る。
- hizukuri は、Wayland compositor そのものの名前ではない。
  基盤になるランタイム、エディター、標準で用意するものを含む、全体の名前である。
- hizukuri で作る Wayland compositor を、**コンポジター**と呼ぶ。
  各自が、自分専用のコンポジターを作る。hizukuri は、その土台になる。
- ゲームを作るためのものではない。
- 最初の目標は、hizukuri で作ったコンポジターを、日常のデスクトップとして使える水準に達することである。
  その先で、一般に普及することを目指す。

### プロジェクトとコンポジター

| 用語 | 意味 |
| --- | --- |
| プロジェクト | エディターで開いて編集する、ディレクトリの全体。スクリプト、shader、シーンの定義のほかに、最適化する前の 3D モデルや、参考の画像など、制作に使う素材も置く |
| コンポジター | プロジェクトをビルドして得られる、最終の成果物。ランタイムが読み込んで動かす |
| ランタイム | コンポジターを読み込んで、Wayland compositor として動かす実行ファイル |

- プロジェクトと、コンポジターは、一致しない。プロジェクトには、コンポジターに入らない素材が含まれる。
- コンポジターは、単独で動く実行ファイルではない。ランタイムが読み込んで動かす。
  単独で動く実行ファイルを生成する機能は、持たない。

## 2. 組み込みの機能を持たない

この節が、設計全体の前提である。

- **コアに、完成された機能を組み込まない。** 組み込みのレンダラーも、組み込みのウィンドウ管理も持たない。
- 次の形は、取らない。
  - Niri 風のレイアウトをコアに組み込み、スクリプトからはパラメータを調整するだけにする。
  - 3D のレンダラーの仕様をコアに組み込み、利用者は、シーンに置くものを選んでスクリプトを少し書くだけにする。
  - レイアウトやルールを宣言的に書く設定言語として、スクリプトを位置づける。
- スクリプトの層で、ゲームエンジンでゲームを作るのと同じ自由度で、すべてを書ける。
  描画の方法、シーンの表現、毎フレームの処理、ウィンドウの管理が、すべてスクリプトの層にある。
- hizukuri が標準で用意するコンポジターも、標準で用意する render pipeline も、この同じ仕組みの上に作る。
  利用者が作るコンポジターと、立場は同じである。
- 多くの利用者は、標準の render pipeline と、それが定めるシーンの形式を使って作る。
  それでも基盤としては、レンダラーとシーンの表現を一から作れる水準を保つ。

コアが受け持つのは、スクリプトの層では作れない部分である。Wayland のプロトコルの処理、ウィンドウの内容をテクスチャとして
取り込むこと、入力をウィンドウへ届けること、GPU と出力装置を扱うこと、色空間の変換（5 節）、などが当たる。
コアとスクリプトの層の境界は、まだ決めていない。

コアは、スクリプトの層が動かないときのための、最小の描画と配置を持つ。これを **fallback** と呼ぶ。
スクリプトが壊れても、開いているウィンドウを表示し、操作を続けられるようにするためのものである。
fallback は、復旧のための仕組みであり、コンポジターの機能ではない。見た目や使い心地を作り込む対象にしない。

## 3. 描画

- **Scriptable Render Pipeline を、スクリプトの層で作れる。**
  ここで言う Scriptable Render Pipeline は、Unity のものより低い層を指す。
  Vulkan のラッパーをスクリプトから呼び、GPU を使う描画を、自分で一から組み立てられる。
- **シーンの表現も、スクリプトの層で定義する。**
  「シーンの表現は固定で、レンダラーだけを差し替える」形にはしない。
  render pipeline ごとに、受け取るシーンの形式が違ってよい。2D 用なら 2D の座標を持つシーン、3D 用なら 3D の座標、
  場合によってはマテリアルや shader のパラメータを持つシーン、という具合である。
  シーンの形式は、render pipeline と組になる。
- **3D は第一級である。** 3D を除外する設計にしない。
  render pipeline を自分で作れる以上、「2D か 3D か」という区別は、基盤にとって意味を持たない。
  2D のシーンで作ったものを、3D のシーンの中に配置する、という組み合わせもできる。
- 基盤として欠かせないのは、次の 3 つである。
  - GPU を使う描画を、自由に書けること。
  - ウィンドウの内容を、テクスチャとして取り込めること。
  - 自由に配置したウィンドウへ入力を届けるための、座標の逆変換を組み込めること。

## 4. スクリプト

- スクリプトに任せる範囲は、2 節と 3 節を実現するのに必要なすべてである。
  毎フレームの Update を含めて、すべての処理を、API の呼び出しとして書ける。
- 言語に求めることは、次のとおりである。
  - ネイティブ並みの速度は要らない。
  - コンパイルの手順なしで使える。
  - render pipeline、ウィンドウの管理、イベントを受けてウィンドウを並べ替える処理を書けるだけの、柔軟さがある。
  - Rust から呼び出しやすい。
- **スクリプト言語は、まだ決めていない。**

## 5. カラーマネジメント

- **すべてが入っていること。** 「HDR に仮に対応した」「ICC に少し対応した」という水準では足りない。
- **VFX のアーティストが業務で使って、色に問題が出ない水準**にする。OCIO に、完全に対応する。
- HDR のディスプレイを、正しく扱う。
- 合成の作業用の色空間は、コアに組み込まない。OCIO の config の色空間から、設定で選ぶ。既定は ACEScg である。
- 色の計算の正解は、OCIO の CPU の計算のうち、近似を使わないものとする。GPU での計算は、これと一致することを確かめる。

### 色空間の変換は、コアが受け持つ

スクリプトを書く人が、色空間について理解していなくても、ウィンドウを正しい色で合成できる。
そのために、色空間の変換を、入口と出口で、コアが受け持つ。

- **入口。** ウィンドウの内容は、ウィンドウが申告する色空間から、作業用の色空間へ、コアが変換する。
  スクリプトと shader が触れる時点で、ウィンドウの色は、作業用の色空間になっている。
  - 変換は、shader がウィンドウの内容を読むときに、コアが提供する関数の中で行う。変換済みのテクスチャを、あらかじめ作ることはしない。
  - 変換済みのテクスチャが要るときは、色空間を変換しながら別のテクスチャへ写す描画を、スクリプトから呼ぶ。この描画は、コアが提供する。
  - ウィンドウの色（表示装置に向けて仕上がった色）を、作業用の色空間へ持ち込むときは、OCIO の既定の動作に従う。
    OCIO の組み込みの config では、tone mapping をしない変換（Un-tone-mapped）である。ウィンドウの白は、作業用の色空間でも白になる。
- **スクリプトの層。** レンダラーは、作業用の色空間のまま、2D の合成や 3D の描画を行い、作業用の色空間のバッファを返す。
  スクリプトの中で色空間を変えなければ、すべてが作業用の色空間にそろった状態で、描ける。
- **出口。** 作業用の色空間のバッファから、それぞれのモニターへ向けた変換は、コアが行う。
  - モニターごとに、OCIO の display と view を当てる。そのあとで、モニターの較正（ICC のプロファイル）を当てる。
  - **既定の view は、tone mapping をしない変換（Un-tone-mapped）である。** 色空間の変換は行うが、明るさを圧縮する曲線はかけない。
    既定では、コンポジターは、ウィンドウの色を変えずに、モニターへ届ける。
    制作用のソフトウェアが、自分で表示用の変換を済ませて出した色を、そのまま見られる。
- スクリプトや shader の中で、作業用の色空間から、ほかの色空間へ変換して処理することは、できる。
  それは、上級の使い方であり、変換の正しさは、書く人の責任である。

### 色の変換を、誰が決めるか

| 範囲 | 決める人 | 内容 |
| --- | --- | --- |
| レンダラーの内部 | コンポジターを作る人 | 作業用の色空間の中で、どう描くか。コアが提供する OCIO の変換の描画を、特定のウィンドウや、描画の結果にだけ、かけることもできる（HDR の動画のウィンドウにだけ tone mapping をかける、3D の描画の結果に view をかける、など） |
| 入口と出口の変換 | コア | ウィンドウの色を、作業用の色空間へ持ち込む変換と、作業用の色空間のバッファを、モニターへ出す変換 |
| 入口と出口の変換の設定 | コンポジターを使う人 | 作業用の色空間、モニターごとの display と view、OCIO の config（view、look、LUT の定義）、モニターのプロファイル |

コンポジターを使う人は、モニターごとの view や、OCIO の config を変えることで、コアが行う変換を、上書きできる。

### 明るさの基準

- 作業用の色空間の値の 1.0 は、どのウィンドウにとっても、そのウィンドウの reference white（画面の中の、ふつうの白の明るさ）である。
  SDR のウィンドウの白も、HDR のウィンドウの reference white も、1.0 になる。HDR のウィンドウの、それより明るい部分は、1.0 を超える値になる。
- 出口で、コアが、1.0 を、モニターの reference white に合わせる。HDR のモニターでは、SDR の内容の明るさとして、コンポジターを使う人が設定する。
- 既定の動作は、Wayland の color-management-v1 の勧め（どのウィンドウの reference white も、同じ明るさにする）に従う。
- この対応は、ウィンドウごとに、上書きできる。たとえば、SDR のウィンドウを、HDR のモニターの上で、どのくらいの明るさで出すかを、
  ウィンドウの種類ごとに変えられる。

### スクリプトに書く色の値

スクリプトや shader に書く数値は、色であるとは限らない。色として渡すか、数値のまま渡すかを、書く人が選ぶ。

- **色として渡す。** 値を、ある色空間の色として解釈し、作業用の色空間へ変換してから、渡す。
  既定では、sRGB の色として解釈する（`#ff8800` のような書き方は、sRGB の色である）。
  ほかの色空間の値として書くこともできるが、その場合は、色空間を明示する。
- **数値のまま渡す。** 変換しない。色ではない値や、すでに作業用の色空間になっている値に使う。

この 2 つは、API の上で、別の書き方になる。

### 読み込む画像

読み込む画像も、色であるとは限らない（法線の map、LUT、データを入れたテクスチャなど）。色の値と同じように、読み込むときに、書く人が選ぶ。

- **色の画像として読み込む。** 画像に埋め込まれた色の情報をもとに、作業用の色空間の値として読めるテクスチャにする。
  色の情報が無い画像は、sRGB として扱う。既定は、こちらである。
- **データとして読み込む。** 変換しない。

### テクスチャの形式

- テクスチャやバッファの形式は、コンポジターを作る人が、自由に指定できる。
- 形式を指定しなくても、作業用の色空間の色を持つのに適した形式が選ばれる API を、あわせて用意する。ふだんは、こちらを使う。
  この API が選ぶ形式は、32 bit の浮動小数点（`RGBA32F`）である。加工していないウィンドウの色が、モニターへ出すときに、元の値に戻るようにするためである。
  16 bit の浮動小数点（`RGBA16F`）では、作業用の色空間が広い原色のとき、一部の色が、元の値に戻らない。
  速さやメモリを優先する場合は、コンポジターを作る人が、別の形式を指定する。
- ウィンドウの内容のテクスチャの形式は、コアが決める。

## 6. コンポジターが満たす水準

hizukuri で作ったコンポジターが、Wayland compositor として満たせる水準である。

- ウィンドウマネージャーとして、まともに使える。ふつうに使われるアプリケーションが、まともに動く。
- **ゲーム向けの機能は、初期の目標に含める。** ティアリングをはじめ、ゲームに必要な機能は、すべて入れる。
- X11 のアプリケーションは、xwayland-satellite に任せる。自前の XWM は持たない。
- IME は、ふつうに使えること。候補ウィンドウの位置が正しく出る、など、通常の IME の利用ができる。
- DRM/KMS の session として、日常使いできる。
- nested でも動く。開発と、エディターからの再生に使う。

## 7. コンポジターの管理

- ランタイムは、コンポジターをインストールして管理する機能を持つ。そのための GUI を持つ。
- コンポジターを、CLI から切り替えられる。
  不具合のあるコンポジターで画面が使えなくなっても、別の仮想端末から入れ替えて、復旧できる。
- 他人が作ったコンポジターを入れて使うことより、自分で作ることを、主な使い方として想定する。

## 8. 標準で用意するもの

- 標準のコンポジターとして、Niri のようなスクロール型タイルのワークスペースを持つものを用意する。2 節のとおり、同じ仕組みの上に作る。
- 標準の render pipeline を、3 種類用意する。組み込みではなく、標準の実装である。
  - 2D に特化した、簡易的なもの。
  - 軽量な 3D のリアルタイムレンダラー。
  - 重量級の 3D のリアルタイムレンダラー。
- 標準の render pipeline のソースコードには、コメントを付ける。
  利用者が、それを手本にして、自分のものを手早く作れるようにする。

## 9. エディター

- エディターは、ゲームエンジンのエディターに当たる GUI のツールである。
  プロジェクトを開き、シーンの配置、スクリプトなど、コンポジターを作るのに必要なものを、すべて操作できる。
  ゲームエンジンと違うのは、再生して確かめる対象が、ゲームではなくウィンドウマネージャーである点だけである。
- エディターは、ランタイムとは別のプロセスである。
- エディターは、hizukuri のコアとは別のものである。
  ふつうの GUI アプリケーションとして作り、hizukuri で作ったコンポジターの上で、1 つのウィンドウとして動く。
  hizukuri 自身の描画の仕組みで、エディターの UI を作ることはしない。
- コアは、シーンの形式に依存しない。エディターは、標準の 3 種類の render pipeline のシーンの形式を扱える。
- 最初の試作では、GUI のツールキットに gpui を使う。足りない機能があれば、gpui を fork する。
  gpui は、最初の試作に限った選択である。後で別のツールキットに置き換えられるように作る。
- エディターの IME は、GUI のツールキットの対応に任せる。
- エディターで作ったものを、その場で再生して、動作を確かめられる。
  一時的に、フルスクリーンで再生できる。フルスクリーンの再生からは、エディターへ戻ってこられる。

## 10. AI からの操作

- MCP サーバーのような仕組みを用意し、AI がエディターを操作できるようにする。
  作ってほしいシーンを AI に伝えて、作ってもらえるようにする。
- そのために、サンプルと説明を、全面的に充実させる。AI は、それらを参照して、独自のシーンを作る。
- スクリーンショットの撮影、fps や GPU の負荷の計測を、MCP を通して行える。

## 11. 技術の前提

- 実装言語は Rust。
- GPU は Vulkan。**Vulkan 1.4 を前提にする。** 最新の拡張機能を前提にしてよい。
- **descriptor heap の拡張（`VK_EXT_descriptor_heap`）を使う。** 従来の descriptor の仕組みを、引きずらない。
- バインディングは vulkan-rs を使う。
- shader の言語は、Slang に統一する。shader のコンパイラーも、Slang のものだけを使う。
- コンポジターの shader は、エディターの側の層が、Slang から SPIR-V へコンパイルする。
  ビルドしたコンポジターに入るのは、SPIR-V である。
- ランタイムは、Slang のコンパイラーを同梱する。OCIO は、色の変換を、shader のソースとして実行時に生成する。
  それをコンパイルするためである。
- shader は、浮動小数点の計算を厳密に行う指定でコンパイルする。最適化で、色の値が変わることを避けるためである。

## 12. 範囲の外

- hizukuri でゲームを作ること。
- 単独で動く実行ファイルの生成。
- コンポジターを共有するサイトや、配布の仕組み。
- 自前の XWM。
- hizukuri 自身の描画の仕組みで、エディターの UI を作ること。
